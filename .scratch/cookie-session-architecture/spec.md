# Cookie 会话架构：后续改造的决策依据

本记录保留 2026-10-10 评审与实验中可用于后续改造的取舍。已经实现的协议细节由 [Cubence 契约](../../docs/agents/site-integrations.md#cubence-account-contract) 维护；本文件不重复旧缺陷清单。Safari 原生验证由其他任务负责，不属于这里的后续工作。

## 先区分要解决哪一种隔离

| 需求 | 可选方案 | 不能顺带承诺的能力 |
| --- | --- | --- |
| 同一操作的身份校验、写入和读回使用同一凭据 | operation 开始捕获 Cookie 快照，按请求 URL 解析其作用域 | 不冻结用户浏览器登录态，不接管服务端 Cookie 轮换 |
| 扩展请求不借用当前网页账号，也不覆盖网页 Cookie | 扩展发起方限定的 DNR 请求头规则、`credentials:omit`、禁止重定向，并协调规则生命周期 | 不隔离页面存储，不等于多账号网络请求并发 |
| 依赖页面 SDK、CSRF 或易失状态的业务 | 复用同源页面；有证据需要时延长页面租约 | 整段持有页面不能阻止用户或站点脚本改会话 |
| Cookie、localStorage、IndexedDB、Service Worker 都独立 | 真正的容器或 profile | 成本包括跨浏览器能力、登录管理与资源；不能用请求头覆盖替代 |

新增适配器先核实原生身份凭据和轮换事实，再决定采用哪一层。推理 key、UI localStorage 用户缓存、登录 Cookie 的角色不能互相替换。

## 为什么 operation 与页面租约分开

operation 固定凭据选择和本次已验证事实；页面租约管理执行资源。两者不必同寿命。已有暖页池能复用页面，尚无证据证明让每个复合操作全程占页更快；长租约还会扩大页面自身请求受到规则影响的窗口。

只有站点要求保留同一页面的易失 SDK/CSRF 状态，或实测重复获取页面成为主要成本时，才考虑延长租约。届时复用现有调度，避免叶子请求再次获取已经持有的锁。operation 不是事务：多次写入仍须分别处理部分成功、取消和未知结果。

当前复用入口是 [Cookie operation session](../../src/services/apiTransport/cookieOperationSession.ts)。站点拥有登录 Cookie 名称、身份校验和协议；公共层拥有凭据捕获、URL 作用域与执行约束。多个适配器若确实出现相同编排，再抽取最小公共操作入口，避免另造一套队列或通用工作流 DSL。

## 哪些性能优化可以继续考虑

| 优化 | 适用条件 | 必须保留的边界 |
| --- | --- | --- |
| 同一 operation 内复用身份响应 | 多个步骤确实重复核验同一快照 | 手动余额刷新读新数据；不能沿用几分钟前打开编辑器时的身份 |
| pending-only single-flight | 测量发现并发身份读取重复 | 区分账号、凭据版本、store 与独立取消者；不解决串行重复或错误凭据降级 |
| 缩小 DNR 排队范围 | 测量证明共享锁等待是主要成本，且能证明规则匹配范围不重叠 | 按规则冲突划分，而非仅按 accountId；所有可能命中规则的扩展请求都需协调 |
| 延长身份缓存 TTL | 有可靠的身份变化与失效信号 | HttpOnly/环境会话缺乏可靠信号时，不缓存已完成的身份结果；余额与身份也不共用 TTL |

测量应同时记录冷启动/暖页耗时、身份读取与业务写入次数、锁等待、窗口及焦点变化。原实验的单次 HTTP 耗时不足以选择产品默认方案。

## 如果未来接管 Cookie 轮换

现有快照不是完整私有 Cookie jar。2026-10-10 的实验只能观察响应 Set-Cookie，并未实现作用域、轮换及持久化。若站点真的依赖响应更新会话，先确认哪些请求会轮换、旧凭据是否仍有效、轮换能否在账号身份不变时安全接纳。

实现前需要定义：响应属于哪个账号与凭据版本；Domain/Path/Secure/过期/分区和删除语义；并发响应如何避免旧值覆盖新值；取消或 worker 重启后怎样恢复。还要评估响应头观察权限与重定向语义，验证不会把扩展账号的 Set-Cookie 写入普通网页账号。不能因保存凭据失效而静默改用环境 Cookie，也不能直接把浏览器账号 B 的凭据写回保存账号 A。

## 已有证据能支持到哪里

真实 Cubence 临时密钥 CRUD 已在没有站点页面、没有浏览器 Cubence Cookie 的 Chromium 145.0.7632.6 中完成：私有凭据与站点 Origin 经 DNR 注入，`credentials:omit`、`redirect:error`。这支持该部署 API 直连的可行性，不证明全部 Cookie 站点或页面交互都可直连。空 403 变为参数校验 400 只证明请求进入不同校验阶段，不能替代成功写入及读回。

Chromium 145.0.7632.6 与 Edge 154.0.4258.62 的本地合成实验分别让扩展 A 请求等待、扩展 C 排队、普通网页 B 独立完成，服务端收到正确的三组凭据；响应也未改写网页 B Cookie。它支持扩展发起方隔离与串行规则方案，不证明三个真实 Cubence 账号，也不证明 A/C 网络并发或完整响应 Cookie 管理。

复验优先扩展 [隔离 E2E](../../e2e/cookieRequestIsolation.spec.ts) 和 [真实浏览器 DNR 场景](../../e2e/dnrRequired/accountCookieDnrRealBrowser.spec.ts)：覆盖同 URL/不同方法、不同账号与网页交错、规则安装失败、迟到安装/清理、取消、worker 重启及重定向。指定凭据无法兑现时必须零业务请求；读请求的 dispatch 不能制造写入不确定性。新增路线必须验证这些边界，不能仅看 DNR Promise 已完成或 API 可调用。
