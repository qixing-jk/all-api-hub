# NexaVlinks check-in and key-creation contract

Status: implemented; successful native-page execution remains unverified.

## Scope and decisions

- One request, two surfaces: adapt daily check-in for `https://asia.nexavlinks.com`, and fix key creation in the extension, which the user reported as broken.
- **Copy unified on one generic key.** Every "the page requires verification you must finish" case now emits `providerFallback.nativePageVerificationRequired` (New API Turnstile path ×2, DaiGua, native-page path, NexaVlinks). The key selects the troubleshooting hint across locales; a locale-copy test asserts that the copy names no widget. Previously persisted `turnstileManualRequired` results retain a compatibility mapping to the generic copy and troubleshooting hint; no separate legacy locale entry is needed.
- **Site type: existing `sub2api`.** Evidence, not branding: the deployed bundle contains a `sub2api-auth-token-refresh` channel name; `SUB2API_AUTH_STORAGE_KEYS` (`auth_token`, `refresh_token`, `token_expires_at`, `auth_user`) match the deployment's `localStorage` exactly; `SUB2API_KEYS_ENDPOINT` (`/api/v1/keys`), `/api/v1/groups/available`, `/api/v1/groups/rates`, `/api/v1/announcements`, and the `{code, message, data}` envelope with `code: 0` all match. No new site type, credential store or adapter family was added.
- **Domain discovery (initial investigation snapshot):** `asia.nexavlinks.com` was the console (nginx, serving `/dashboard`, `/check-in`, `/keys`). `www.nexavlinks.com` served the marketing site only, with no observed dashboard or check-in routes. `eu.`, `us.`, `na.`, `api.`, and `app.` did not resolve. No other regional console was advertised by the site itself at that time.
- **Key-creation root cause (confirmed against the live API):** this deployment rejects any key write whose payload *mentions* `ip_whitelist`, even as `[]`, with `403 { code: 403, reason: "API_KEY_ADVANCED_SETTINGS_ADMIN_ONLY", message: "custom keys, IP restrictions, and rate limits are restricted to administrators" }`. The extension's editor always sent `ip_whitelist` on create, so every create from the extension failed while the site's own UI (which omits the field) succeeded. `quota` (0 and 5), `expires_in_days`, and `group_id` singular are all accepted; `group_ids: [19, 21]` is the site's own multi-group form, and the server derives `group_id` from it. There is no public capability flag: `/api/v1/settings/public` exposes no indicator, so the restriction is server-side only.
- **Fix scope:** omit an empty `ip_whitelist` from the *create* payload only. The edit path sends a field only when it actually changed, and clearing an existing whitelist must still round-trip as `[]`, so update keeps its current behaviour. A non-empty whitelist on this deployment still 403s; `classifyFailureCode` already maps 403 to `PermissionDenied` with the upstream code preserved.
- **Check-in method: `nexavlinks:daily-checkin`, probed on every Sub2API candidate.** Originally gated by origin, then changed to the family standard after review: the only origin-gated Sub2API method is AI-ROUTER, and its gate exists because that protocol is served from a *different* origin than the account's dashboard. ToolCode, Hiyo, DaiGua, Sidrune, 小白Code, 詞元, 登仙 and FreeAPI are all single named deployments and none are gated, because their protocol lives on the account's own origin — same as here. Contract captured from the deployment's own `CheckInView-*.js` and `CheckInChallengeDialog-*.js` chunks plus live authenticated reads: `GET /api/v1/check-in?timezone=<IANA>` reads status, `POST /api/v1/check-in` claims, `GET /api/v1/check-in/challenge` mints the puzzle.
- **Cost of un-gating, accepted deliberately:** every Sub2API account now probes one more read-only route (feedback status routes 10 → 11), and seven existing assertions had to be updated — three count fixtures, two sibling-discovery tests that needed the new probe mocked to 404, and two post-save discovery tests whose self-built registry fixture had to mirror the 11th candidate. `postSaveDiscovery.ts` reads `getAutoCheckinCandidateMethodIds` straight from the real registry while the test mocks its own provider registry, so an unlisted candidate resolves with no detector and silently changes which method wins. Sibling deployments are picked up without registration, which is the point.
- **Status DTO differs from the FreeAPI/Clawhud siblings:** no `enabled` field. It reports `checked_in_today`, `eligible`, `current_streak`, `recent_records[]`, `today_record`, and `settings { captcha_mode, balance_type, daily_reward, consecutive_rewards }`. `eligible: false` until today's or yesterday's usage clears the deployment threshold, so availability is `checked_in_today || eligible !== false` — a completed account is still an enabled method. This path is `/api/v1/check-in`, distinct from Hiyo's `/api/v1/checkin`, so no sibling discriminator entry was needed.
- **Execution drives the site's own page instead of posting a claim.** The claim body needs a puzzle answer (`{captcha_id, captcha_angle}` for rotate, `{captcha_id, captcha_points}` for click/slide) that only a person can give, and `settings.captcha_mode` exists only to describe that puzzle — so it no longer drives the decision. The provider opens `/check-in`, clicks the page's claim button with a `clickText` trigger scoped to `main button`, lets the person finish the challenge in the opened window, then confirms through the read-only status. An unfinished verification returns `MANUAL_VERIFICATION_REQUIRED`; an unconfirmed click returns `CHECKIN_UNCONFIRMED`. The shared `resolveNativePageFailureResult` mapping moved into `providers/shared.ts` so this path and the New API native-page path use one implementation. A claim body is never invented: the extension has no observed contract for it.
- **Reward is left unset.** The award is credit-denominated (`amount: 0.5`, `balance_type: "gift"`, group `rate_multiplier` 0.12x–1x), not a verified USD amount, so `readUsdReward` would misstate it next to the account's quota.
- **Locale:** `translateAutoCheckinMessageKey` resolves the generic verification key through a literal `t()` call that the extractor can enumerate. The legacy key is accepted only as an input alias. Extraction integrity and completeness checks passed for all eight app locales after the review fixes.
- **Error-code precedence:** deployment `reason` values must pass the existing `readSafeUpstreamCode` format check (at most 64 characters, letters/digits/underscore/dot/hyphen). A valid reason may refine a numeric code; an invalid reason falls back to that code. `SESSION_BINDING_MISMATCH` remains authoritative even when a reason is present, because authentication recovery relies on it.

## Validation boundaries

- Investigation recorded authenticated status reads and successful key API writes using the fixed payload. These observations do not establish a successful operation through the extension UI.
- A fresh check-in through the extension, native puzzle detection and manual completion remain unverified: the available account was ineligible and required a solved puzzle.
- Captcha-free deployments, other regional consoles and long-term credential expiry were not verified.
- Redeem API submission, rebate statistics, subscription purchasing and fork-specific multi-group key editing are out of scope. Existing family capabilities remain the owners for invite links, announcements, usage and model catalogs.
- Regression coverage lives in the NexaVlinks transport and provider tests, Sub2API key editor/resource and response decoder tests, and check-in presentation, discovery and feedback tests.
