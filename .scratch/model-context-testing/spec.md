## 结论与范围

建议在现有 API 验证的工具区增加按需执行的上下文测试，分别报告当前连接的最大可接收输入和任务有效上下文。第一版限纯文本；图片、工具 schema、多轮对话和自动压缩需另行设计。

观测对象是所选账号或凭证、请求模型、协议、请求配置和时间共同确定的连接。中转路由、模型别名和服务端策略可能改变结果，不能据此认证模型身份，也不能把连接上限当成底层模型的固有能力。

| 结果 | 测量对象 | 可下的结论 |
| --- | --- | --- |
| 声明容量 | 官方文档或模型目录元数据 | 声明支持的输入/输出限制，未经实测 |
| 可接收输入 | 当前连接完成请求的输入长度 | 已验证下界、明确拒绝上界，或只测到配置上限 |
| 有效上下文 | 指定任务、长度与信息位置的正确率 | 在当前测试条件和阈值下的有效长度 |

所有长度区分目标 token 数、估算 token 数、服务端报告输入 token 数和请求字节数。上下文窗口、最大输入与最大输出不一定是同一个限制；固定输出预算后测得的是该预算下的输入能力。

## 最大可接收输入的方法

1. 先做短输入基线，确认协议和连接能生成完整响应。基线失败时停止容量搜索。
2. 用带种子的合成自然文本逐级扩大，例如 4K、8K、16K、32K；使用短固定回答以控制输出开销。长度包含测试指令、问题与消息包装，不能只计算填充文本。
3. 同时设定输入长度、累计输入 token、请求次数和单请求时间上限。没有可靠价格时仅显示用量估算；达到任何预算即停止。
4. 只有明确的上下文超限错误才构成容量拒绝上界。在已有成功点与明确容量拒绝点之间二分，直到分辨率达到配置值。网关 HTTP 413 单独记录为请求体限制。
5. 429、鉴权失败、5xx、网络超时、取消和输出被截断不收缩容量区间。一般 HTTP 400 也不能自动当容量拒绝；保留脱敏代码和有限诊断，不认识的错误显示不确定。
6. 复测边界附近的成功点。若出现更小输入失败而更大输入成功，记录非单调结果，停止给出单一边界。
7. 达到用户配置的测试上限时只显示“已验证至少 X”，不能显示“最大 X”。例如成功 96K、明确超限 100K，展示区间而非虚构精确值。

短回答只能证明请求完成。可额外在前、中、后放置随机校验信息，检索失败仍属于内容利用失败，不能直接证明静默截断。服务端 usage 与本地计数明显不一致也只是诊断线索；可信 token 计数和网关证据不足时标记“输入完整性未确认”。

## 有效上下文的方法

采用可控合成任务，从最容易自动判分的三类开始。借鉴 RULER 的任务设计，不在未复刻题库、生成方式和评分规则时使用“官方 RULER 分数”的名称。

[NVIDIA 官方 RULER 仓库](https://github.com/NVIDIA/RULER)和[论文](https://arxiv.org/abs/2404.06654)提供 13 个任务、4 类能力，并说明简单单针检索接近满分仍可能掩盖复杂长上下文任务的退化。原始有效长度阈值参照 Llama2-7B 在 4K 的 85.6%，并非普适阈值；主分支旧运行说明已标记 deprecated，复现时须固定官方版本及对应流水线。

[Greg Kamradt 的 NIAH 原始实现](https://github.com/gkamradt/LLMTest_NeedleInAHaystack)提供按长度和插入深度扫描的参考，并记录种子、实际位置、usage 等复现信息。第一版适合借鉴扫描方法和确定性答案；本研究未完整核实 Lost in the Middle 与 NoLiMa 正文，后续关联检索设计若采用它们，需补充原始证据。

| 任务 | 构造 | 自动评分 |
| --- | --- | --- |
| 单信息检索 | 在干扰文本中插入随机实体与随机值，询问其值 | 完整字段精确匹配 |
| 多信息检索 | 多个相近实体、多个目标值，问题要求全部返回 | 每个目标召回率与全题正确率分别报告 |
| 跨段关联 | A 指向 B，B 对应值；两条线索放在不同段落 | 最终值精确匹配，并记录线索位置 |

答案只存在于测试正文，不放在 system、问题或示例中。加入相似实体干扰，并用短上下文基线排除题目本身难度或输出格式不兼容。负例问题要求回答不存在；单独统计误报。

长度采用分档采样，位置至少覆盖前部、中部、后部，例如 10%、50%、90%。位置应按 token 偏移计算；只有估算计数时注明位置也是近似值。跨段任务记录每条线索的位置。用多组固定种子重测，保留题库版本、种子与生成配置供复现。

每个长度按任务和位置显示正确数/有效样本数。快速模式可少量采样，用于发现明显下降；严谨模式增加种子和位置，同时报告样本数与置信区间。拒绝、网络失败和取消不能作为正确题，也不能混入能力错误率；另列完成率，样本不足的格子不能判为达标。

有效长度的阈值是产品配置，不能当成业界统一标准。可选示例：各必选任务/位置均达到 90% 正确率且满足最低有效样本量；要求从短基线到该长度的全部已测档位满足条件。若出现通过、失败、再通过，应展示曲线与波动，而非挑最大的通过点。

单针检索成功只说明这一类检索有效。有效上下文结果必须带任务名与阈值，不能推广到写代码、复杂推理或整个模型。关联检索可以后续增加低词面重叠任务，避免单纯字符串匹配带来过于乐观的结果。

## Token 与费用

按用户确认的方向，优先复用已有模型元数据缓存与身份匹配，再决定声明容量、tokenizer 和测试参数。不要在上下文测试模块另造模型名称匹配规则或远程目录缓存。

### 复用现有元数据的顺序

1. 通过 `modelMetadataService.initialize()` 加载或复用缓存，再调用 `resolveModelIdentity(modelId)`。现有返回值明确区分 `resolved`（`exact` / `normalized-alias`）、`ambiguous` 和 `unmatched`；有歧义不能取第一条结果。
2. 匹配成功后读取 `metadata.limits.context/input/output` 作为声明限制，读取 `provider_id/family/id` 作为 tokenizer 选择的依据。缺失或不合理的限制保持未知，不能自动变成零或无限大。声明限制只用于展示与建议测试档位，不是实测结论，也不自动授权发送到完整容量。
3. 当前 `ModelMetadata` 类型和归一化器没有 tokenizer/encoding 字段。若远程数据确有这些字段，先在现有元数据 owner 归一化并保留来源，再由计数器读取；不得假定缓存已提供该信息。
4. 若没有显式 tokenizer 信息，使用解析出的标准模型身份匹配 tokenizer 库支持的型号或经过验证的编码映射。仅凭厂商、模型 family、别名或 OpenAI-compatible 协议不足以保证编码正确；证据不足时标为估算。不要把用于重定向的宽松 `findStandardModelName` 匹配当成 tokenizer 已确认。
5. 接口支持的官方计数端点可用于校验完整请求。保留元数据模型身份、身份匹配方式、缓存更新时间、tokenizer 名称/版本与计数来源；本地文本编码计数不能冒充服务端完整请求计数。服务端 usage 是接口报告值，中转场景下不等于独立验证。
6. 一次测试开始时固定元数据、编码与参数快照。沿用 `useModelMetadataLookup` 的忙碌期间延后更新规则，避免后台刷新在测试中途改变长度与位置口径。

未知模型仅报告估算，不使用“字符数除以四”作为精确结果；允许在后续高级配置里显式选择编码，但选择值仍需保留来源和验证状态。

Gemini 官方文档提供请求前的 `count_tokens` 和响应后的输入、输出、思考及缓存用量字段，因此事前计数与实际消耗应分开保存。[Google token 文档](https://ai.google.dev/gemini-api/docs/generate-content/tokens)

以独立请求执行各个样本，不启用工具或搜索。固定支持的输出预算和采样配置；不支持的参数明确记录，不能默默切换协议或生成模式。禁用测试请求的自动重试，让每次发送都可计数；允许用户明确重测失败样本。缓存输入仍计入上下文长度，费用估算需要区分普通输入、缓存输入与输出。

## 仓库落点（已读代码）

- `src/services/models/modelMetadata/ModelMetadataService.ts`、`types.ts` 和 `modelIdentityIndex.ts`：已有 models.dev 元数据内存缓存（24 小时刷新间隔）、声明限制归一化与保留歧义的身份解析。优先使用这一 owner，避免平行缓存。`src/hooks/verification/useModelMetadataLookup.ts` 已提供验证 UI 的闲时更新边界。
- `src/services/verification/aiApiVerification/providers.ts`：复用 `createModel`，传递 `requestHeaders`、请求 profile、协议和模型；不新建绕开现有认证的客户端。
- `src/services/verification/aiApiVerification/probes/probeGeneration.ts`：当前只返回文本、工具结果等，未返回 usage/finishReason。容量测试需要扩展这一共享结果契约，或在其最小适合的共享层提供可观测生成结果；保留现有流式错误与取消语义。
- `src/services/verification/modelQuality/`：作为任务生成、判分及容量搜索的服务归属候选。React 状态仍放在 feature 层。
- `src/features/Verification/api/VerificationToolsPanel.tsx` 与 `useVerificationTools.ts`：已有按需绘图工具和凭证解析接口，可作为上下文工具入口。执行协调应沿用 Verification Run Session 的取消/失效规则，避免无限增大现有 hook。
- `src/services/verification/verificationResultHistory/`：现有历史是摘要。扩展时只存紧凑统计、配置版本和复现种子；不持久化大段合成 prompt、原始响应或凭证。存储 schema、sanitizer、保留策略与迁移一起调整。
- 网页验证已有后台委派路径；先落实现有对话框中的工具，再决定是否支持网页侧长任务。不能直接把大 prompt、每题响应和进度全塞进跨上下文消息。

## 建议交付顺序与验收

1. 完成生成用量、结束原因和 token 计数来源的契约，再实现有限预算的输入边界搜索。
2. 加入单信息、多信息、跨段关联的合成任务与确定性判分，输出长度/位置结果表。
3. 加入取消、进度、历史摘要和可导出的脱敏报告；结果曲线表达能力变化，位置热力图表达中部退化。

按仓库 TDD 规则，先写失败行为测试：元数据事实优先于名字猜测；歧义身份不能自动选编码；缺失 tokenizer 仍标估算；缓存刷新不改变活动测试的计数口径；声明容量不能写成实测容量；明确容量拒绝才二分；达到上限仅报告下界；超时、取消、413 和非单调结果不误判；答案没有从问题泄漏；多目标评分不接受部分字符串；预算停止后不再发送；旧 session 不能发布结果或启动历史写入。再实现并跑相关 Vitest、compile、knip、翻译键检查和必要的 UI 验收。真实模型验证需在有明确请求预算的阶段执行。

初始研究未调用真实模型。当前实现已通过合成接口和浏览器流程验收；各协议计数端点经中转站是否可用、真实长输入的内存/消息开销、不同推理模型的输出预算适配，以及结果的统计稳定性仍缺少真实模型证据。
