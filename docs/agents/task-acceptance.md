# Automated task acceptance

Use this workflow before handing off implemented changes. The agent owns execution and evidence collection within the task's existing authorization. Reuse the project's Vitest, Playwright and live-extension runners; keep checks proportional to the affected behavior. Documentation-only and instruction-only changes need a diff, reference and consistency review rather than application tests or screenshots.

## Account for the behavior changes

Build a task-local acceptance table from the requested outcomes and the final task-owned diff. Include intentional behavior changes discovered during implementation, including defaults, compatibility and recovery behavior. For behavior-preserving refactors, identify the observable contracts being preserved. Reconcile the table after the last implementation change so that every outcome has a result or an explicit gap.

| Outcome / scenario | Before | Expected after | Automated assertion / command | Result and evidence |
| --- | --- | --- | --- | --- |
| Concrete user action and preconditions | Previous observable result | Intended observable result | Test name or reproducible runner command | Passed, failed, blocked, not run, or not applicable; artifact link and reason for any gap |

Select applicable success, empty, failure, partial-success and retry/cancel scenarios from the changed flow. Test shared behavior at its public boundary and use representative callers for integration risk. Follow the existing TDD requirement for features and bug fixes. Screenshots alone do not verify persistence, request semantics, authentication, or resource cleanup; assert those outcomes through the appropriate public interface and readback.

Run the selected checks automatically when prerequisites are available. If a promised path lacks reusable automation, extend the closest maintained test or runner within the authorized scope. Record any path that could not run and its missing prerequisite, then continue independent checks. A command listed in a report without being executed is not passing evidence.

## Compare changed UI

Apply visual review to changes in rendered appearance, content or layout, including changed UI states. A behavior-only change with no visual effect needs the affected behavior checks; it does not require screenshots merely because it touches a UI file. For a new surface with no predecessor, review the after image and label before as not applicable. Explicit user requests for particular comparisons still apply.

For an existing surface, select representative checkpoints before editing when practical and reuse comparable captures already retained in the task. The default before state is the task's pre-change UI, including relevant existing work, rather than an unrelated main-branch version. During iterative refinements, compare the final result with the task baseline; add an intermediate comparison when it answers the user's latest question. Do not rebuild unchanged versions or rerun unrelated flows solely to regenerate valid screenshots.

Image inspection is a task-level acceptance checkpoint, not a gate after every edit, test run or generated report. Baseline and comparison artifacts primarily support developer review: capture and retain them without requiring the agent to view them. Agents prioritize the representative final result. Batch small refinements and review their final combined result. During intermediate edits, use targeted behavior assertions and text-based layout/style measurements for the known risk; those checks support iteration but do not replace final visual judgment. Reopen images only for a concrete new visual question, an unexpected assertion/diff result, a materially different layout/state, or a user request for visual assessment. Reuse prior inspection when the affected rendering and capture inputs remain unchanged; visible changes still need final review.

Capture matching fixtures, browser/platform, viewport, device scale, language, theme and interaction state. Record revision/build identities and relevant uncommitted changes for both captures. Use a separate worktree/build only when an older version must be reconstructed; preserve the current worktree and index. Wait for UI, data and fonts to settle and disable animations. Cover the affected layout and risk-relevant responsive, theme or recovery variants, rather than every possible combination. Prefer focused panels with enough surrounding context to assess layout.

Use screenshots of the actual tested UI where available; deterministic fixtures in the real application are valid when labelled. An isolated component preview can answer a bounded styling question, but record its fixture, styles and limitations. A before image must come from the recorded earlier source/build or a verified equivalent fixture. Changing props, classes or DOM in the current implementation to imitate the old UI is a simulated preview, not evidence that the earlier version was rendered. Ensure previews load the applicable application styles and fonts; a visible DOM or matching data attribute alone does not establish styled fidelity or runtime integration.

Inspect a focused representative final image with the client's image viewer when visual judgment is needed. Do not routinely load baseline, side-by-side, full-gallery or pixel-diff images into the model. Open them only to answer a concrete comparison question, such as investigating a suspected regression or assessing an unclear requested change. Use an existing comparison runner when available; a stitched preview is useful for developer review, while a generated pixel difference is optional unless an existing visual assertion, the regression risk or the user requires it. Generate and retain evidence separately from loading it into the model: neither generating a report nor retaining an artifact requires an image-viewing call. Avoid creating one-off exporters or comparison frameworks merely to satisfy an artifact checklist. For maintained visual regression checks, use Playwright screenshot assertions and retain expected, actual and diff images for mismatches. Do not update baselines, widen tolerances or mask changed content merely to make the check pass. Explain normalization of volatile content. Label manual review as manual and say which images were inspected; retained developer comparisons need not have been viewed by the agent. Saving images or generating a pixel diff is not an automated pass criterion.

Review the whole affected panel as well as the changed element: hierarchy, alignment, text wrapping, spacing, button proportions and consistency with shared UI. For shared components, inspect representative consumers with different content or actions. Describe the observed result against the user's requested outcome; passing geometry or class assertions alone does not establish visual quality.

If a genuine baseline or compatible environment cannot be obtained within the task's scope, retain the current screenshot and report the exact gap; do not fabricate a before state or claim comparison passed. An after-only image establishes future coverage. Missing comparison evidence remains a visual acceptance gap, separately reported from passing behavior checks, and does not require an unrelated environment project or a new permission checkpoint.

## Keep evidence reproducible

Keep the task-local report and review-only images outside Git, using an existing ignored output directory or a verified task-local exclusion. Retain separate run directories so later runs do not overwrite before images or useful failures. Only deliberately maintained fixtures and visual-test baselines belong in version control.

Record the tested revision/build, target, environment prerequisites by name, commands, actual results and artifact paths. Link each table row to the relevant assertion and evidence. Preserve failure artifacts even if a retry passes, and report the retry rather than treating it as proof that a flaky failure was fixed. Evidence from an older tree can be reused only when the affected behavior and relevant build inputs remain unchanged.

For live extension work, follow the project's `live-extension-ui-automation` skill. Site integration evidence and previews follow [evidence storage](../../.agents/skills/add-site-integration/references/evidence-and-validation.md) and [visual previews](../../.agents/skills/add-site-integration/references/visual-previews.md). Preserve existing authenticated automatic-capture policies. Local raw evidence stays local; prepare and inspect a separate shareable copy before any authorized publication.

## Handoff

Provide the complete behavior-change table inline for a small change, or link the task-local report and summarize it for a larger change. Include executed checks and results, commands to reproduce them, and a decisive inline visual preview when applicable. Reuse retained artifacts in the handoff without another image-tool call; displaying a developer comparison does not require the agent to inspect its baseline first. For a comparison, label and display before and after together, either as separate images or a combined preview; include clickable artifact/report links and any generated diff. A path-only list is not a visual preview. If the client cannot render local images, provide clickable links and state that limitation. Make unverified paths, missing baselines and environmental blockers visible. Keep local validation and requested remote PR reconciliation separate; pending required evidence leaves acceptance incomplete.
