# 自動認識トラブルシューティングガイド

このページでは、プラグインの「アカウント追加/編集」で **自動認識** をクリックした際に発生する、認識に時間がかかりすぎる、無限待機、認識失敗（401/403/フォーマットエラーなど）、および送信できないなどの問題のトラブルシューティングについて説明します。

## Requesty：管理キーを作成して認識する

`https://app.requesty.ai` を入力し、**Requesty 管理キーを作成して認識**をクリックします。拡張機能はこのブラウザーの Requesty ログインセッションで管理キーを作成し、検証後にアカウント情報を入力します。フォームにキーがある場合は、そのキーを再利用します。

このサイトのアカウントが既に保存され、その管理キーがまだ有効な場合は、新規作成せずにそのキーを再利用し、その旨を表示します。作成されるキー名は `All API Hub - Account Connection (xxxxxxxx)` で、API Keys ページで見分けられます。Requesty はキー名を変更できないため、不要になったキーは削除してください。

管理キーはアカウントの認証情報であり、クライアントに渡すキーではありません。キー管理ではアカウント自身の認証情報として表示され、表示とコピーはできますが、エクスポートや一括エクスポートの対象にはならず、既定キーにも選ばれません。組織内の他のキーをすべて作成・削除できるためです。推論には別の通常キーを使用してください。まだ無い場合は自動設定で作成されます。

未ログインの場合は Requesty にログインして再試行してください。自動作成できない場合は、API Keys ページで **Admin Permissions** を有効にしたキーを作成し、フォームに貼り付けます。作成結果が不明な場合は、重複作成を避けるため、先に API Keys を確認してください。取得済みのキーが検証に失敗しても、再試行できるようフォームに保持されます。

## 認識に時間がかかりすぎる（「認識中...」のまま）

自動認識は一時的なページを開いてサイト情報を読み取る必要があるため、以下の状況では明らかに遅くなります。

-   **サイトで Cloudflare / ファイアウォール認証が有効になっている場合**：一時的なウィンドウがポップアップ表示されたかどうかを確認してください。手動で認証を選択する必要がある場合は、タイムアウトする前に認証を完了してください。
-   **ネットワーク/サイトの応答が遅い場合**：しばらく待つか、ネットワーク/プロキシを切り替えてから再試行することをお勧めします。
-   **権限不足**：拡張機能が対象サイトにアクセスできることを確認し、選択した認証方式に必要な権限を付与してください。詳しくは [権限管理](./permissions.md) を参照してください。

## 認識失敗：まず本当にログインしていることを確認してください

自動認識は、同じブラウザで対象サイトにすでにログインしていることに依存します。

1.  まずブラウザで対象サイトの管理画面（コンソール）ページを開きます。
2.  ログインページにリダイレクトされていないことを確認します（ページを一度更新して検証します）。
3.  その後、プラグインに戻り自動認識を実行します。

## 認識失敗：認証方法の切り替えを試してください

サイト/カスタマイズバージョンによってインターフェースとログイン状態の処理が異なるため、認識失敗時にはまず認証方法の切り替えを試してください。

-   **アクセストークン認証失敗**：**Cookie認証** に切り替えてから再度自動認識を実行してください。
-   **AnyRouter**：**Cookie 認証**を設定します。通常の操作は保存済みアクセストークンやサイトのログイン状態で成功する場合があるため、成功しても保存済み Cookie の有効性は確認できません。

Cookie 認証欄の互換認証の説明は各サイトに適用されます。通常の操作はアクセストークンやブラウザーの現在のログイン状態で成功する場合があり、成功しても入力した Cookie の有効性や更新は確認できません。トークンの通知は、アカウントに実際にアクセストークンが保存されている場合にのみ表示されます。ブラウザーのセッションのみを使うサイトでは、固有のログイン状態の説明も維持します。Cookie 認証に対応し、アカウントの識別情報を独立して取得できるサイトでは Cookie の検証を利用できます。ログイン復旧には個別の対応が必要で、現在は AnyRouter の Cookie と Sub2API のトークンに対応しています。

## AnyRouter：ログインの自動復旧

**この Cookie を検証**をクリックすると、入力した Cookie が対象アカウントのものとしてサイトに受け入れられるかを独立して確認できます。この結果はアカウントの状態とは別です。Cookie が拒否されても、他の認証情報で通常の操作が成功する場合があります。通信エラー、サイトの認証、権限の制限では有効性を判断できません。検証は再ログインや認証情報の変更、通常のリクエスト認証の変更を行いません。Cookie を編集したら再検証してください。自動復旧は通常の操作が明確に認証を拒否された場合に開始します。

1. **アカウント編集**の Cookie 認証欄の横にある **ログイン復旧を設定**をクリックするか、編集画面のセクション一覧で **アカウントログイン**を選びます。
2. GitHub、Linux DO またはパスワードログインを選び、必要な情報を入力してから **ログインを自動復旧**を有効にして保存します。設定はアカウントごとに保存され、初期状態では無効です。パスワードログインには、サイトのログインユーザー名とパスワードが必要です。
3. 残高更新、キーの読み込み・コピー、チェックインで認証エラーが出た場合も、**ログイン復旧を設定**からそのアカウントのログイン設定を開けます。設定または修正を保存して、元の操作を再試行してください。概要画面の関連する認証警告にも同じ入口があります。

検証で Cookie の拒否やアカウントの不一致が確認された場合、設定済みのログイン方法で手動復旧できます。未設定の場合は、そのままログイン設定を開けます。手動復旧では取得した Cookie を独立して検証し、対象アカウントとの一致を確認してから編集中の値に反映します。保存済みの認証情報を置き換えるには保存が必要で、自動復旧も有効にはなりません。アカウントの識別情報が分かっている場合、AnyRouter の Cookie を手動で取り込む際も先に検証し、検証に失敗した場合は元の値を保持します。

残高の更新、キーの読み取り、チェックイン時にサイトが明確に認証を要求すると、拡張機能は選択した方法でログインを試みます。アカウントの本人確認後、保存済み Cookie を更新して操作を続けます。既存のチェックイン方法は変わりません。ネットワークエラーやサイトの認証ページではログイン復旧を開始しません。サイトの認証、アカウントの不一致、またはログイン結果を確認できない場合は、その復旧を停止します。

AnyRouter のサイトはログイン時に自動チェックインする場合があるため、ログインの復旧でもサイトのチェックインが実行されることがあります。既に完了している場合は、後続のチェックイン要求でサイトが返した「チェックイン済み」の結果を使用します。

## Sub2API：ログイン復旧とトークンの自動更新

手動追加は JWT Access Token だけで開始でき、Refresh Token を先に手動取得する必要はありません。「アカウント編集 → アカウントログイン」で対応するログイン方法を選び（パスワードログインではメールアドレスとパスワードを入力）、**ログインの自動復旧**を有効にして保存します。設定はアカウントごとで、初期状態では無効です。

拡張機能は保存済みの Refresh Token による更新を優先し、新しい Access Token、Refresh Token、有効期限をまとめて保存します。Refresh Token がない場合、または更新が拒否されブラウザーのセッションでも復旧できない場合は、認証の失敗が確認された後に設定済みの方法でログインします。新しい Access Token のアカウント識別情報を独立して検証し、サイトから返されたトークンと更新情報を保存します。次回からは Refresh Token を追加入力せずに自動更新できます。

旧版やカスタマイズされたサイトが Refresh Token を返さない場合は、検証済みの Access Token だけを保存し、古い更新情報を削除します。CAPTCHA、二要素認証、OAuth の承認には操作が必要な場合があります。識別情報の不一致、キャンセル、アカウント設定の変更があった場合、古いログイン結果で上書きしません。コンソールと API のオリジンが分離され、既存のログイン機能が対応していない環境では、この復旧機能を表示しません。キーの変更操作には追加のログイン再試行を行わず、対応済みのチェックイン復旧では状態と実行条件を再確認します。

## 認識されたサイト種別が正しくない

自動認識は決まった順序でシグナルを取得します。まずドメイン、次にデプロイが自身について公開しているサイト名（サイトの `/api/status` が返す `system_name`）、最後にページタイトルです。そのため、画面のタイトルが標準の「New API」のままでも、その背後でカスタマイズ版が動いているデプロイは、公開されているブランド名で種別を認識できます。

認識結果が実際のサイトと一致しない場合：

-   「アカウント編集」で **サイト種別** を正しい種別に手動で変更して保存してください。サイト種別は拡張機能がどのインターフェース群を呼ぶかを決めるため、ブランド名よりも重要です。
-   どれを選べばよいか分からない場合は、まずそのアカウントのチェックインを一度実行する（**クイックチェックイン**）か、「アカウント編集」で **チェックイン方法を再検出** をクリックしてください。拡張機能がサイト自身のシグナルから種別を推定し、「アカウント編集」の通知、自動チェックインの実行結果、キー管理の失敗ヒント、「概要」の「対応が必要」リストに書き出します。
-   種別を変更したら、もう一度認識して、利用可能なチェックイン方法が見つかることを確認してください。

このヒントは、アカウントがその時点で記録されたサイト種別を保持している間だけ表示されます。サイト種別を変更すると古い記録は無効になり、すでに離れた種別名を表示し続けることはありません。以降の読み取りでサイトが保存された種別と一致した場合も同様に無効になります。

## 送信できない / 保存できない：必須項目を一つずつ確認してください

必須項目が不足している場合、送信ボタンが無効になるか、保存に失敗します。必要な項目はサイトごとに異なるため、まずサイト種別を確認し、対応する項目をチェックしてください。

-   **New API と互換サイト**：サイト名、ユーザー名、ユーザー ID、Access Token、0 より大きいチャージ金額レートを確認します。Cookie 認証を使う場合は、セッション Cookie（Header 値）を取り込むか入力します。
-   **Sub2API**：サイト名、ユーザー ID、JWT Access Token、チャージ金額レートを確認します。Cookie 認証には対応していません。「拡張機能管理セッション（複数アカウント）」を有効にした場合は、Refresh Token の取り込みまたは入力も必要です。
-   **OpenRouter**：サイト名、OpenRouter Management Key、チャージ金額レートを確認します。ユーザー ID は不要で、Cookie 認証にも対応していません。
-   **その他のサイト**：フォームに現在表示されている必須マークと、[アカウント手動追加ガイド](./add-account.md#manual-addition)の該当サイトの説明に従ってください。

## 最後の手段：アカウントの手動追加
自動認識が常に完了しない場合は、**手動追加** に切り替えて、情報を補完し、その後アカウントを保存することができます。

詳細は [アカウント手動追加ガイド](./add-account.md#manual-addition) を参照してください。
